# Security and Privacy

## 1. Threat model and scope

Merlin is a local-first personal desktop application that may hold API credentials, provider account metadata, project documents, and private screenshots.

Primary concerns:
- Secret exposure through database, logs, Markdown, backups, or source control.
- Accidental document overwrite or loss.
- Unsafe process launching.
- Path traversal or unintended filesystem access.
- Sensitive data exposure to future AI integrations.
- Malicious or malformed external content.

This document defines application security requirements, not a claim of formal security certification.

## 2. API secrets

- Store raw API keys in Windows Credential Manager.
- SQLite stores only non-secret metadata and credential references.
- Never write raw secrets to Markdown, logs, crash reports, analytics, or source control.
- Mask keys by default.
- Reveal requires explicit user action.
- Copy requires explicit user action.
- Do not automatically test keys against providers in v1.
- Ensure errors do not include secret values.
- A screenshot or attachment must never be used to store a full API key or other secret. Full secrets must be redacted before import; encryption at rest does not make an unredacted import acceptable.

If the import flow, a local detector, or the user identifies a potentially exposed secret, do not import the attachment. Explain that a redacted replacement is required. If a potentially exposed attachment was already imported, immediately block further rendering, sharing, and export of that managed attachment; instruct the user to rotate or revoke the exposed secret; and offer a purge of every managed active copy, preview, thumbnail, revision, backup copy, trash entry, and pending export that contains it. Do not automatically rewrite an external repository copy or retract an already completed external export; identify the affected external location when known and require the user to redact or remove it there.

## 3. Filesystem boundaries

- Restrict file operations to explicitly registered project Docs roots and Merlin-managed storage.
- Canonicalize and validate paths before operations.
- Prevent path traversal and symlink escapes where relevant.
- Use atomic writes and verify destination state before replacement.
- Do not delete files based only on watcher events.
- Preserve snapshots before destructive changes.

## 4. Custom launch actions

Allowed action types:
- Application
- Terminal
- URL
- Folder

Requirements:
- Validate URL schemes; allow only intended schemes such as `https`.
- Validate executable and working-directory paths.
- Prefer argument arrays over shell-string interpolation.
- Do not build a generic unrestricted shell executor.
- Display configured terminal commands clearly.
- Avoid passing secrets in command-line arguments.
- Handle failures without exposing sensitive environment data.

## 5. Database and logs

- Use parameterized SQL.
- Apply schema migrations.
- Avoid logging document contents or credentials.
- Store only the metadata required for diagnostics.
- Protect database writes with transactions where multiple records must remain consistent.
- Document backup and restore behavior.

## 6. Docs and attachments

- Follow the three-way sync rules in `DOCS-AND-VAULT.md`.
- Never silently overwrite a divergent copy.
- Preserve recovery snapshots.
- Preserve document source independently from rendering. HTML and MDX are source constructs, not executable content.
- Render only a sanitized Markdown representation. The HTML allowlist is limited to `p`, `br`, `h1`–`h6`, `ul`, `ol`, `li`, `blockquote`, `hr`, `pre`, `code`, `em`, `strong`, `del`, `table`, `thead`, `tbody`, `tfoot`, `tr`, `th`, `td`, `details`, `summary`, `a`, `img`, and disabled task-list `input` elements. The allowed document-controlled attributes are `a[href,title]`, `img[src,alt,width,height,title]`, and `input[type=checkbox,checked,disabled]`; any IDs needed for headings, syntax classes, and diagram markup are generated by Merlin's trusted renderer rather than accepted from document HTML. Strip scripts, event handlers, styles, forms, frames, embeds, object elements, custom elements, inline SVG, and every unlisted element or attribute. Unsupported content remains available in source mode without being executed.
- Never evaluate MDX expressions, imports, exports, JSX components, or scripts from project documents. Render MDX as inert source or require source-edit mode.
- Mermaid source may be rendered only by a renderer configured without external fetching, callbacks, script execution, or unsafe HTML. Phase 0 must prove that configuration; until then, show Mermaid as an inert code block.
- Resolve relative document links and image paths only after canonicalizing them inside the configured Docs root or Merlin-managed attachment store. Rendered images may use only those validated local references; do not fetch remote images while rendering documents.
- Permit document hyperlinks only to in-document anchors, validated relative Docs paths, and `https` URLs. An external URL opens only after an explicit user click and in the system browser, never by automatic navigation or inside a privileged WebView. Reject `file`, `javascript`, `data`, custom, and other unapproved schemes.
- The document-rendering surface must not receive Tauri command bindings or privileged capabilities. Sanitized document content communicates with Merlin only through non-privileged rendering data; native operations remain behind typed commands initiated by Merlin-owned controls.
- Sensitive screenshots/attachments must not be sent to external services automatically.
- Sensitive private attachments and every Merlin-managed derivative, including versions and trash, require authenticated encryption at rest. Protect the encryption key with the current Windows user's OS-backed protection (for example DPAPI); do not silently fall back to plaintext when that protection is unavailable. Phase 0 must validate the chosen Rust/Tauri mechanism and document backup and recovery limits. Encryption complements, and never replaces, redaction.
- An explicit export may create a user-chosen external copy. Before exporting sensitive attachments, warn that Merlin cannot purge or recall that external copy; do not leave unencrypted temporary export material behind.
- Future AI features require explicit user selection and consent for content being sent.

## 7. Usage Journal privacy

Never collect:
- Document contents
- API keys/passwords
- Clipboard contents
- Screenshots
- Keystrokes
- External application activity

Provide pause, clear, export, and retention controls. Keep the journal local.

## 8. Future AI and integrations

AI features are deferred. If introduced:
- BYOK is optional.
- Clearly show what content will be sent.
- Require explicit confirmation for sensitive content.
- Do not send API-key screenshots or private attachments by default.
- Keep local functionality available without AI.
- Do not expose secrets to coding agents through automatic context injection.

## 9. Security testing

Include tests for:
- Secret redaction.
- Attachment import refusal, quarantine/purge behavior, and removal from managed versions, trash, previews, and pending exports.
- Credential reference handling.
- Path validation and traversal.
- URL scheme validation.
- Launch argument handling.
- Sync conflict preservation.
- Atomic write failures.
- Database query safety.
- Attachment access boundaries.
- Markdown sanitization, MDX/script non-execution, URL/path policy, and absence of Tauri capabilities in the document-rendering surface.
